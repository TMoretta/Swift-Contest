\section{Linee guida progettuali}\label{sec:linee-guida-progettuali}
La progettazione di \textbf{Swift Contest} è stata guidata da principi di ingegneria del software moderni, volti a garantire un sistema robusto, sicuro e manutenibile, anche in un contesto di sviluppo rapido.
Le linee guida principali sono state:
\begin{itemize}
    \item \textbf{Separazione delle responsabilità (SoC)}: è stata applicata una netta separazione tra il livello di presentazione (UI), la logica di presentazione (ViewModel) e il livello di accesso ai dati (Model/Repository), fondamentale per la testabilità e la manutenibilità del codice.
    \item \textbf{Sicurezza come requisito primario}: è stato adottato un modello di accesso ai dati basato sul \textbf{Principio del Minimo Privilegio (Principle of Least Privilege)}, dove il client è considerato intrinsecamente non sicuro.
    L'accesso al database è negato per default e concesso selettivamente solo tramite un'API sicura.
    \item \textbf{Architettura Client-Server con backend BaaS}: è stata adottata una moderna architettura Client-Server.
    Il client (sviluppato in Flutter) gestisce la presentazione e la logica di UI, mentre il server è rappresentato da una piattaforma \textbf{Backend-as-a-Service (BaaS)} come Supabase.
    Questo approccio permette di delegare la gestione dell'infrastruttura (database, autenticazione, storage) e di distribuire la logica di business in modo flessibile tra il client e le funzioni serverless (RPC ed Edge Functions).
    \item \textbf{Sviluppo cross-platform}: la scelta di un framework come Flutter ha permesso di massimizzare il riuso del codice tra le piattaforme target (Android e Web), ottimizzando i tempi di sviluppo.
\end{itemize}

\section{Architettura del frontend: il pattern MVVM con BLoC}
\label{sec:frontend-architecture}
Il frontend è stato sviluppato in Flutter seguendo i principi dell'architettura \textbf{MVVM (Model-View-ViewModel)}, implementata attraverso il pattern \textbf{BLoC (Business Logic Component)}.
Questa scelta permette di ottenere una netta separazione delle responsabilità, garantendo testabilità e manutenibilità.
La struttura del codice sorgente in \texttt{lib/} riflette questa suddivisione:
\begin{itemize}
    \item \textbf{View (\texttt{/view})}: il livello di presentazione, composto dai Widget di Flutter che costituiscono l'interfaccia utente.
    Questo livello si limita a mostrare i dati ricevuti dal suo ViewModel (il BLoC) e a notificare gli eventi di interazione dell'utente (es.\ la pressione di un pulsante).
    \item \textbf{ViewModel (\texttt{/viewmodel}, implementato come BLoC)}: il cuore della logica di presentazione.
    Ogni BLoC riceve eventi dalla View, esegue la logica di business (spesso invocando un metodo del Model/Repository), e produce uno stream di stati a cui la View reagisce per aggiornarsi.
    \item \textbf{Model (\texttt{/model})}: il livello di accesso ai dati.
    È composto dai \emph{Repository}, che fungono da unica interfaccia verso il backend, astraendo le chiamate a RPC ed Edge Functions.
    Include anche le \emph{Entities} (le rappresentazioni dei dati del dominio) e i \emph{Bundles} (oggetti aggregati per ridurre il numero di chiamate di rete).
\end{itemize}

\subsection{Implementazione del ViewModel: il pattern BLoC}\label{subsec:implementazione-del-viewmodel:-il-pattern-bloc}
Per la gestione dello stato e l'implementazione del ViewModel, è stato adottato il pattern BLoC, utilizzando il pacchetto \texttt{flutter\_bloc}.
La scelta di BLoC è motivata dalla sua natura reattiva e basata su stream, che si integra perfettamente con il paradigma dichiarativo di Flutter.
Questo pattern impone un flusso di dati unidirezionale e prevedibile:
\begin{enumerate}
    \item La \textbf{View} notifica un \textbf{Evento} (es. \texttt{LoginButtonPressed}).
    \item Il \textbf{BLoC} riceve l'evento, esegue la logica di business (es.\ chiama \texttt{authRepository.login()}) e, al termine, emette un nuovo \textbf{Stato} (es. \texttt{LoginSuccess} o \texttt{LoginFailure}).
    \item La \textbf{View}, tramite un widget come \texttt{BlocBuilder}, si mette in ascolto dello stream di stati e si ridisegna per riflettere il nuovo stato.
\end{enumerate}
Questo approccio garantisce che la logica di business sia completamente disaccoppiata dalla UI, rendendola facilmente testabile in isolamento.
I BLoC sono stati organizzati in due categorie: \textbf{globali} (es. \texttt{AuthBloc}, \texttt{InboxBloc}) e \textbf{di pagina} (es. \texttt{JurorVotingProcedurePageBloc}).

\subsubsection{Gestione centralizzata degli errori nel repository}
Una delle responsabilità principali del livello \emph{Model} (e in particolare dei \emph{Repository}) è quella di agire come un robusto intermediario tra la logica di business e il backend.
Questo include non solo il recupero dei dati, ma anche una \textbf{gestione centralizzata e sicura degli errori}.

Le chiamate a un backend come Supabase possono fallire in molti modi: problemi di rete (\texttt{SocketException}), errori di autenticazione (\texttt{AuthException}), errori del database (\texttt{PostgrestException}), ecc.\ Esporre queste eccezioni direttamente al livello del BLoC o della UI sarebbe problematico per due motivi:
\begin{enumerate}
	\item Creerebbe un forte accoppiamento tra la logica di presentazione e le librerie specifiche del backend.
    \item Potrebbe esporre all'utente finale messaggi di errore tecnici e potenzialmente sensibili.
\end{enumerate}

Per risolvere questo problema, è stata creata una funzione di ordine superiore, \texttt{handleBackendCall}, che ``avvolge'' ogni chiamata al backend.
Come mostrato nel listato seguente, questa funzione utilizza un blocco \texttt{try...catch} per intercettare le eccezioni specifiche di Supabase e le mappa in classi di \textbf{Failure} personalizzate e sicure.
Queste \emph{Failure} sono oggetti semplici che rappresentano un fallimento in modo astratto (es. \texttt{NetworkFailure}, \texttt{ServerFailure}), senza contenere dettagli tecnici.
Il tipo di ritorno \texttt{Either<Failure, T>} permette al BLoC di gestire in modo pulito e tipizzato sia il caso di successo (a destra) che quello di fallimento (a sinistra).

% LISTATO: Funzione di gestione centralizzata degli errori.
\begin{lstlisting}[language=Dart, caption={Funzione helper per la gestione sicura delle chiamate al backend.}, label={lst:handle_backend_call}]
	/// Avvolge una chiamata al backend, gestendo e mappando le eccezioni.
	Future<Either<Failure, T>> handleBackendCall<T>(
	Future<Either<Failure, T>> Function() function,
	) async {
		try {
			// Esegue la funzione che contiene la chiamata al backend.
			return await function();
		} on SocketException catch (e) {
			// Errore di rete (es. no internet).
			Logger.warning('Network error: $e');
			return Either.left(const NetworkFailure());
		} on AuthException catch (e) {
			// Errore di autenticazione di Supabase.
			Logger.warning('Auth error: $e');
			return Either.left(authExceptionToFailure(e));
		} on PostgrestException catch (e) {
			// Errore del database PostgreSQL.
			Logger.warning('Postgrest error: $e');
			return Either.left(postgrestExceptionToFailure(e));
		} on FunctionException catch (e) {
			// Errore durante l'invocazione di una Edge Function.
			Logger.warning('Edge function error: $e');
			return Either.left(edgeFunctionExceptionToFailure(e));
		} on StorageException catch (e) {
			// Errore nello Storage (es. upload fallito).
			Logger.warning('Storage error: $e');
			return Either.left(storageExceptionToFailure(e));
		} catch (e) {
			// Qualsiasi altro errore non previsto.
			Logger.error('Unknown error: $e');
			return Either.left(const Failure());
		}
	}
\end{lstlisting}

\subsubsection{Gestione dell'uguaglianza degli oggetti con Equatable}
Per ottimizzare le performance e garantire un comportamento prevedibile nella gestione dello stato, tutte le entità, i bundle e gli stati dei BLoC estendono la classe fornita dal pacchetto \texttt{equatable}.

Questa scelta implementativa è cruciale per due motivi principali.

Il primo riguarda il corretto funzionamento del pattern BLoC. Di default, Dart confronta gli oggetti per riferimento, non per valore.
Ciò significa che due istanze di un oggetto, anche se contengono dati identici, vengono considerate diverse.
Senza \texttt{Equatable}, un BLoC potrebbe emettere un nuovo stato identico al precedente, causando una ricostruzione non necessaria e dispendiosa dell'interfaccia utente.
Utilizzando \texttt{Equatable}, invece, il confronto avviene basandosi sul valore degli attributi dell'oggetto.
Questo permette ai widget di Flutter, come \texttt{BlocBuilder}, di determinare in modo efficiente se uno stato è \emph{realmente} cambiato prima di procedere con la ricostruzione, prevenendo refresh superflui della UI e migliorando significativamente la reattività dell'applicazione.

Il secondo motivo, altrettanto importante, riguarda la \textbf{robustezza e la chiarezza della logica di business}.
Spesso, durante lo sviluppo, sorge la necessità di confrontare due oggetti per verificare se rappresentano la stessa entità concettuale, anche se sono istanze diverse in memoria.
Estendendo \texttt{Equatable}, si ottiene un'implementazione standard e priva di errori dell'uguaglianza basata sul valore, semplificando la logica di confronto all'interno dei BLoC e dei Repository e riducendo il rischio di bug sottili legati al confronto per riferimento.

\subsection{Navigazione con AutoRoute}\label{subsec:navigazione-con-autoroute}
La gestione della navigazione è stata affidata al pacchetto \texttt{auto\_route}, che genera un router fortemente tipizzato, eliminando l'uso di stringhe per le rotte e riducendo il rischio di errori a runtime.
Un elemento chiave è l'\texttt{AuthGuard}, una classe che intercetta le richieste di navigazione e verifica lo stato di autenticazione dell'utente tramite l'\texttt{AuthBloc}, reindirizzandolo alla pagina di login se tenta di accedere a una rotta protetta.

% Inserire qui un breve estratto di codice Dart che mostra la definizione di una rotta protetta con l'AuthGuard all'interno del file del router.
\begin{lstlisting}[language=Dart, caption={Estratto del sistema di routing protetto con \texttt{AuthGuard}.}, label={lst:auth_guard}]
	// --- 1. Definizione della rotta protetta (in app_router.dart) ---
	
	@AutoRouterConfig()
	class AppRouter extends RootStackRouter {
		// ...
		@override
		List<AutoRoute> get routes => [
		
		// ... altre rotte pubbliche o di autenticazione
		
		// Esempio di rotta protetta: solo gli utenti autenticati
		// possono accedere alla dashboard dell'organizzatore.
		AutoRoute(
		path: '/organizer-home',
		page: OrganizerHomeRoute.page,
		guards: [AuthGuard(authBloc: authBloc)], // Applica la guardia
		),
		
		// ... altre rotte protette
		];
	}
	
	
	// --- 2. Implementazione della guardia (in auth_guard.dart) ---
	
	class AuthGuard extends AutoRouteGuard {
		final AuthBloc authBloc;
		
		AuthGuard({required this.authBloc});
		
		@override
		void onNavigation(NavigationResolver resolver, StackRouter router) {
			// Controlla lo stato di autenticazione tramite l'AuthBloc
			final isAuthenticated = authBloc.state.authStatus.isAuthenticated;
			
			// Elenco completo delle rotte pubbliche (di autenticazione)
			const authPaths = [
			'/sign-in', 
			'/sign-in-verify', 
			'/sign-up', 
			'/sign-up-verify'
			];
			final targetPath = resolver.route.path.split('/:').first;
			
			if (isAuthenticated) {
				// Se l'utente è autenticato e cerca di andare a una pagina di login/registrazione,
				// lo reindirizzo alla sua home page.
				if (authPaths.contains(targetPath)) {
					resolver.redirect(const RootRoute());
				} else {
					// Altrimenti, può procedere verso la rotta protetta.
					resolver.next(true);
				}
			} else {
				// Se l'utente NON è autenticato...
				if (!authPaths.contains(targetPath)) {
					// ...e sta cercando di accedere a una rotta protetta,
					// lo reindirizzo alla pagina di login.
					resolver.redirect(SignInRoute());
				} else {
					// ...e sta già andando a una pagina di login/registrazione, lo lascio procedere.
					resolver.next(true);
				}
			}
		}
	}
\end{lstlisting}

\subsection{Strategia di navigazione e passaggio dei dati}\label{subsec:strategia-di-navigazione-e-passaggio-dei-dati}
Una scelta architetturale fondamentale, dettata dalla necessità di una perfetta integrazione con il web, riguarda la modalità di passaggio dei dati tra le pagine.
A differenza di un'applicazione puramente mobile, dove è comune passare interi oggetti in memoria durante la navigazione, in un'applicazione web questo approccio è insostenibile: l'utente può ricaricare la pagina o accedere a un URL diretto, perdendo qualsiasi stato tenuto in memoria.

Per questo motivo, il sistema di navigazione di Swift Contest adotta una strategia rigorosa: \textbf{nelle rotte vengono passati solo identificativi (ID) primitivi} (es. \texttt{contestId}, \texttt{juryId}), mai oggetti complessi.
Quando una pagina viene caricata, il BLoC associato riceve l'ID dai parametri della rotta e, come prima azione, invoca il Repository per caricare dal backend tutti i dati necessari.

Questa scelta, sebbene aumenti il numero di chiamate al database, garantisce enormi vantaggi in termini di robustezza e coerenza con il paradigma web:
\begin{itemize}
	\item Ogni pagina è \textbf{ricaricabile} in modo indipendente.
    \item Ogni pagina ha un \textbf{URL univoco e condivisibile} (deep linking).
    \item Il comportamento dell'applicazione è prevedibile e consistente tra la navigazione interna e l'accesso diretto a un URL\@.
\end{itemize}

\subsubsection{Validazione dell'input utente e gestione dei form}
Per garantire l'integrità dei dati e fornire un feedback immediato all'utente, è stata implementata una robusta strategia di validazione dell'input direttamente a livello client, prima che i dati vengano inviati al BLoC e, successivamente, al backend.

Invece di definire la logica di validazione all'interno dei singoli widget, \textbf{tutte le funzioni di validazione sono state centralizzate} in un unico file, \texttt{lib/utils/validators/validators.dart}.
Questo approccio, basato su funzioni pure, offre tre vantaggi significativi:
\begin{itemize}
	\item \textbf{Riutilizzabilità}: La stessa funzione, ad esempio \texttt{emailValidator}, può essere riutilizzata in più punti dell'applicazione (es.\ pagina di login, registrazione, modifica profilo) senza duplicazione di codice.
	\item \textbf{Manutenibilità}: Se una regola di validazione deve essere modificata (es.\ la complessità minima di una password), la modifica viene effettuata in un unico punto, garantendo coerenza in tutta l'applicazione.
\end{itemize}

Il listato seguente mostra un esempio di un validatore complesso e il suo utilizzo all'interno di un widget \texttt{TextFormField}.

% LISTATO: Esempio di validatore centralizzato.
\begin{lstlisting}[language=Dart, caption={Esempio di validatore centralizzato e suo utilizzo in un widget.}, label={lst:validators}]
	// 1. Definizione della funzione di validazione pura
	// in lib/utils/validators/validators.dart
	
	String? passwordValidator(String? value) {
		if (value == null || value.isEmpty) {
			return 'Required';
		}
		if (value.length < 8) {
			return 'Must contain at least 8 characters';
		}
		if (!RegExp(r'[A-Z]').hasMatch(value)) {
			return 'Must contain at least one uppercase letter';
		}
		if (!RegExp(r'[0-9]').hasMatch(value)) {
			return 'Must contain at least one number';
		}
		if (!RegExp(r'[!@#$&*~%^()\[\]\-_=+{};:,.<>?/\\|]').hasMatch(value)) {
			return 'Must contain at least one special character';
		}
		
		return null; // La validazione ha successo
	}
	
	// 2. Utilizzo del validatore in un widget della UI
	
	TextFormField(
	// ... altre proprietà come controller, decoration, etc.
	
	// La funzione di validazione viene passata come riferimento.
	validator: passwordValidator,
	
	// La validazione viene attivata automaticamente al momento
	// del submit del form o in base all'autovalidateMode.
	autovalidateMode: AutovalidateMode.onUserInteraction,
	);
\end{lstlisting}

\subsection{Design system e theming}\label{subsec:design-system-e-theming}
Per garantire un'interfaccia utente coerente e facilmente manutenibile, è stato definito un design system centralizzato basato sul \textbf{Material Design 3}.
La scelta di \texttt{MaterialTheme} come base è stata strategica, in quanto è lo standard de facto per le applicazioni Android e garantisce un'esperienza utente nativa e riconoscibile.

Il cuore del sistema di theming di Material Design è il \textbf{\texttt{ColorScheme}}, un oggetto che definisce una palette di colori predefinita e semanticamente organizzata.
Invece di usare colori specifici i widget fanno riferimento a ruoli di colore come \texttt{primary} (per elementi principali), \texttt{secondary} (per elementi di supporto), \texttt{surface} (per gli sfondi), \texttt{onPrimary} (per il testo da mostrare sopra un colore primario), ecc\@.
Questo approccio permette di cambiare l'intera palette di colori dell'applicazione (ad esempio, passando dal tema chiaro a quello scuro) modificando unicamente l'oggetto \texttt{ColorScheme}, senza dover alterare il codice dei singoli widget.

Tuttavia, il \texttt{ColorScheme} standard non è sufficiente per coprire tutte le esigenze di un'applicazione complessa, che richiede colori semantici personalizzati (es.\ per stati di successo, errore, warning).

Per risolvere questo problema in modo pulito e scalabile, invece di definire colori statici sparsi nel codice, si è fatto ricorso a una funzionalità del linguaggio Dart: le \textbf{estensioni}.
Un'estensione (\emph{extension}) permette di \textbf{aggiungere nuove funzionalità a una classe esistente}, anche se non si ha accesso al suo codice sorgente.
In questo caso, è stata creata un'estensione sulla classe \texttt{ColorScheme} di Flutter per "arricchirla" con i colori semantici personalizzati richiesti dall'applicazione.

Come mostrato nel listato seguente, l'estensione \texttt{ColorSchemeX} aggiunge nuovi \emph{getter} (es. \texttt{success}, \texttt{warning}) alla classe \texttt{ColorScheme}.
Questi nuovi colori diventano così parte integrante del tema e possono essere richiamati in qualsiasi punto dell'applicazione in modo sicuro e coerente tramite \texttt{Theme.of(context).colorScheme.success}, ereditando automaticamente i cambiamenti tra tema chiaro e scuro.

% LISTATO: Estensione ColorSchemeX
\begin{lstlisting}[language=Dart, caption={Definizione dell'estensione \texttt{ColorSchemeX} per aggiungere colori personalizzati al tema.}, label={lst:colorscheme_extension}]
	// in lib/utils/themes/color_scheme_x.dart
	
	extension ColorSchemeX on ColorScheme {
		// Colore per indicare successo (es. notifiche positive)
		Color get success => const Color(0xFF28a745);
		Color get onSuccess => const Color(0xFFFFFFFF);
		
		// Colore per avvisi
		Color get warning => const Color(0xFFffc107);
		Color get onWarning => const Color(0xFF212529);
		
		// Altri colori personalizzati...
	}
\end{lstlisting}

\subsubsection{Gestione del feedback di caricamento: l'OverlayLoader}
Per fornire un feedback visivo all'utente durante le operazioni asincrone, è stato implementato un sistema di caricamento personalizzato, \texttt{OverlayLoader}.
Questo sistema utilizza l'Overlay di Flutter per mostrare un indicatore di progresso con uno sfondo semitrasparente e sfocato, permettendo all'utente di mantenere il contesto visivo della schermata sottostante.

L'implementazione si basa su due scelte di design chiave per garantire robustezza e facilità d'uso:
\begin{itemize}
	\item \textbf{Singleton Pattern}: La classe \texttt{OverlayLoader} è implementata come un singleton per garantire che esista una sola istanza del gestore del loader, prevenendo la visualizzazione di più overlay contemporaneamente.
	\item \textbf{Dart Extensions}: Per semplificare l'invocazione del loader, è stata creata un'estensione sulla classe \texttt{BuildContext}, che permette di usare una sintassi pulita e intuitiva come \texttt{context.showLoader()} e \texttt{context.hideLoader()}.
\end{itemize}

\paragraph{Gestione del ciclo di vita e prevenzione dei ``leak''}
Un aspetto cruciale per la robustezza di questo sistema è la gestione del suo ciclo di vita.
Per evitare che l'overlay del loader rimanga ``bloccato'' sullo schermo se una pagina viene chiusa (\emph{disposed}) durante un'operazione di caricamento (ad esempio, a causa di un errore o della navigazione dell'utente), è stata adottata una pratica difensiva: \textbf{il metodo \texttt{context.hideLoader()} viene sistematicamente invocato all'interno del metodo \texttt{dispose} di ogni pagina} che utilizza il loader.
Questo garantisce che, indipendentemente da come o perché la pagina viene distrutta, qualsiasi overlay di caricamento attivo venga sempre rimosso, prevenendo ``leak'' visuali e garantendo la stabilità dell'interfaccia utente.

% LISTATO: Implementazione del loader non-intrusivo.
\begin{lstlisting}[language=Dart, caption={Implementazione del loader non-intrusivo tramite Overlay e Dart Extensions.}, label={lst:overlay_loader}]
	// 1. Classe Singleton per la gestione dell'overlay
	class OverlayLoader {
		OverlayEntry? _entry;
		
		// Singleton pattern per garantire un'unica istanza
		OverlayLoader._();
		static final OverlayLoader _instance = OverlayLoader._();
		factory OverlayLoader() => _instance;
		
		void show(BuildContext context) {
			if (_entry != null) return; // Evita di mostrare più loader
			
			_entry = OverlayEntry(
			builder: (_) => const Positioned.fill(
			// ObscuredLoader è un widget custom con sfondo sfocato
			child: ObscuredLoader(), 
			),
			);
			
			// Inserisce l'entry nell'overlay radice per essere sempre in cima
			Overlay.of(context, rootOverlay: true).insert(_entry!);
		}
		
		void hide() {
			_entry?.remove();
			_entry = null;
		}
	}
	
	// 2. Estensione su BuildContext per un'API pulita e intuitiva
	extension OverlayLoaderX on BuildContext {
		void showLoader() => OverlayLoader().show(this);
		void hideLoader() => OverlayLoader().hide();
	}
\end{lstlisting}

\subsection{Schema fisico e tabelle principali}\label{subsec:schema-fisico-e-tabelle-principali}
Lo schema del database è composto da una serie di tabelle che implementano le entità del dominio.
Le tabelle cardine includono:
\begin{itemize}
	% --- TESTO AGGIORNATO E DETTAGLIATO PER 'profiles' ---
	\item \textbf{\texttt{profiles}}: Questa tabella estende la tabella \texttt{auth.users} gestita internamente da Supabase.
	Poiché lo schema \texttt{auth} è protetto e non modificabile, per aggiungere attributi personalizzati (es.\ \texttt{full\_name}, \texttt{pref\_role}) è stata creata una tabella parallela nello schema \texttt{public}.
	La colonna \texttt{id} di \texttt{profiles} funge sia da chiave primaria che da chiave esterna verso \texttt{auth.users(id)}, stabilendo una relazione uno-a-uno.
	La creazione del profilo è automatizzata tramite un \textbf{trigger} a livello di database, che inserisce un nuovo record in \texttt{profiles} ogni volta che un utente completa la registrazione.
	\item \texttt{contests}: memorizza le informazioni principali di un concorso.
	\item \texttt{participations} e \texttt{jurations}: implementano le classi di associazione che legano utenti, contest e giurie.
	\item \texttt{works}: contiene i metadati delle opere sottomesse dai partecipanti.
	\item \texttt{voting\_forms} e \texttt{voting\_form\_fields}: definiscono la struttura dei moduli di voto.
	\item \texttt{voting\_sessions}: rappresenta una sessione di voto.
	\item \texttt{voting\_session\_participants}, \texttt{voting\_session\_jurors}: contengono gli snapshot dei dati per una sessione di voto attiva.
	\item \texttt{voting\_form\_submissions} e \texttt{voting\_form\_submission\_values}: memorizzano i voti inviati dai giurati.
\end{itemize}

\subsection{Scelte di design chiave}\label{subsec:scelte-di-design-chiave}
Oltre alla semplice mappatura delle entità, sono state prese decisioni di design cruciali per garantire la robustezza del sistema.

\subsubsection{Integrità referenziale e strategia di cancellazione}
Per garantire la consistenza del database, è stato fatto un uso estensivo dei vincoli di chiave esterna.
Una decisione di design fondamentale è stata quella di adottare una strategia di \textbf{cancellazione fisica (hard delete)} piuttosto che una di \textbf{cancellazione logica (soft delete)}, principalmente per ottimizzare l'uso delle risorse (spazio su database e storage) e per semplificare la logica delle query di lettura.

Data questa scelta, la gestione della cancellazione dei dati correlati è diventata un aspetto critico, risolto con un approccio a più livelli.

\paragraph{Cancellazione a cascata tramite \texttt{ON DELETE CASCADE}}
Per le relazioni di composizione forte e dirette, dove l'entità ``figlia'' non ha dipendenze esterne come file nello Storage, è stata utilizzata la politica \textbf{\texttt{ON DELETE CASCADE}}.
L'esempio più calzante è la relazione tra \texttt{voting\_forms} e \texttt{voting\_form\_fields}.
Poiché i campi di un form non hanno senso di esistere senza il form stesso, l'eliminazione di un record in \texttt{voting\_forms} provoca la cancellazione automatica e a cascata di tutti i record correlati in \texttt{voting\_form\_fields}.
Questo approccio delega interamente la logica di pulizia al database, garantendo massima efficienza e consistenza dei dati con il minimo sforzo implementativo.

\paragraph{Cancellazione tramite trigger per relazioni uno-a-uno}
In alcune relazioni uno-a-uno, la chiave esterna è stata posizionata nella tabella concettualmente ``principale'' per motivi di design.
L'esempio più significativo è la relazione tra \texttt{contests} e \texttt{places}: è la tabella \texttt{contests} a contenere il riferimento \texttt{place\_id} con un vincolo \texttt{UNIQUE}.

Questa configurazione, sebbene sia logicamente corretta, impedisce di usare la politica \texttt{ON DELETE CASCADE} per eliminare un \texttt{place} quando il \texttt{contest} associato viene cancellato.
Per risolvere questo problema e automatizzare la pulizia dei dati, è stato implementato un \textbf{trigger di database}.
Questo trigger si attiva \emph{dopo} (\texttt{AFTER}) l'eliminazione di un record dalla tabella \texttt{contests} ed esegue esplicitamente la cancellazione del record corrispondente nella tabella \texttt{places}, utilizzando l'ID del luogo del contest appena eliminato.
In questo modo, si garantisce l'integrità referenziale e si evita di lasciare record \texttt{places} orfani, delegando anche in questo caso la logica di pulizia al database.

\paragraph{Cancellazione di dati esterni tramite Edge Functions}
La cancellazione a cascata del database non può gestire dati esterni, come i file memorizzati in Supabase Storage.
Per questo motivo, le operazioni di cancellazione più complesse, come l'eliminazione di un utente o di un contest, non vengono eseguite direttamente dal client, ma sono gestite da \textbf{Edge Functions} dedicate (es.\ \texttt{user-delete-account}, \texttt{admin-delete-contest}). Queste funzioni agiscono da orchestratori: dopo aver eliminato i record dal database (che a loro volta attivano le cancellazioni a cascata e i trigger), invocano l'API di Supabase Storage per \textbf{eliminare tutti i file associati} (es.\ immagini del profilo, file dei \emph{Work}), garantendo una pulizia completa e prevenendo la creazione di file ``orfani''.
Questa logica non poteva essere implementata in una funzione RPC, poiché queste non hanno accesso all'API dello Storage.

\subsubsection{Snapshot dei dati tramite denormalizzazione controllata}
Per garantire l'immutabilità e l'auditabilità del processo di voto, è stato implementato un meccanismo di \textbf{snapshot dei dati}, una delle scelte architetturali più importanti del backend.

Quando un organizzatore avvia una \emph{VotingSession} tramite la funzione RPC \texttt{organizer\_start\_voting\_session}, il sistema non si limita a collegare le entità esistenti, ma esegue una forma di \textbf{denormalizzazione controllata}.
Per ogni partecipante e giurato coinvolto, vengono create nuove righe in tabelle di sessione dedicate (es.\ \texttt{voting\_session\_participants}, \texttt{voting\_session\_jurors}).

Queste nuove righe contengono non solo le chiavi esterne ai record originali, ma anche una copia statica degli attributi più importanti al momento dell'avvio.
Come mostrato nel listato seguente, la tabella \texttt{voting\_session\_participants} include, oltre a \texttt{participation\_id}, anche i campi \texttt{participant\_full\_name}, \texttt{work\_name}, ecc.

Una scelta di design cruciale è l'uso della clausola \textbf{\texttt{ON DELETE SET NULL}} sulla chiave esterna \texttt{participation\_id}.
Questo significa che se il partecipante originale dovesse essere eliminato dal sistema, il record dello snapshot \emph{non} verrebbe cancellato, ma manterrebbe solo il riferimento a \texttt{NULL}.
Ciò dimostra che la vera ``fonte di verità'' per la sessione di voto sono gli attributi di snapshot, garantendo che i voti espressi rimangano validi e auditabili anche se le entità originali cessano di esistere.

Lo stesso principio si applica a \texttt{voting\_session\_jurors}, dove \texttt{juror\_id} è fondamentale per tracciare se un giurato ha già votato, ma può essere impostato a \texttt{NULL} in caso di cancellazione dell'account senza invalidare il voto già espresso.

Questa tecnica garantisce:
\begin{enumerate}
	\item \textbf{Integrità della sessione}: se un utente cambia nome, il nome ``congelato'' nello snapshot rimane invariato.
	\item \textbf{Auditabilità e resilienza}: i voti rimangono validi e associati ai dati di snapshot anche se i record originali vengono eliminati.
	\item \textbf{Performance ottimizzate}: i dati denormalizzati vengono letti direttamente, evitando complesse query con join.
\end{enumerate}

\subsection{Implicazioni del design del form di voto sull'aggregazione dei risultati}\label{subsec:implicazioni-del-design-del-form-di-voto-sull'aggregazione-dei-risultati}
Una scelta di design fondamentale, visibile nello schema del database, è che \textbf{ogni giuria è associata a un unico e specifico form di voto}.
Questa flessibilità permette all'organizzatore di creare criteri di valutazione diversi per giurie diverse (es.\ una giuria tecnica con campi slider complessi e una giuria popolare con un singolo campo di preferenza).

Tuttavia, questa decisione architetturale ha un'implicazione diretta e importante su come i risultati possono essere processati e visualizzati, influenzando sia il backend che il frontend: \textbf{il sistema non può aggregare automaticamente i punteggi tra giurie diverse}, poiché i loro form di voto (e quindi i loro criteri e punteggi) non sono direttamente comparabili.

Di conseguenza, tutte le operazioni di analisi dei risultati, sia a livello di logica di backend (RPC) che di interfaccia utente (frontend), sono state progettate per operare a livello della singola giuria:
\begin{itemize}
	\item La \textbf{generazione della classifica} avviene per ogni singola giuria.
    \item L'\textbf{esportazione dei risultati} in formato Excel è granulare e produce un file per ciascuna giuria.
\end{itemize}
Se l'organizzatore desidera creare una classifica ``globale'' che combini i risultati di più giurie, deve farlo esternamente, utilizzando i dati esportati.
Questa è una limitazione consapevole del progetto, un compromesso accettato per garantire la massima flessibilità nella configurazione dei criteri di valutazione.

Per mantenere questa flessibilità anche nella fase finale, il sistema non impone un formato di classifica globale, ma permette all'organizzatore di \textbf{pubblicare qualsiasi classifica in formato PDF}.
Questa scelta di design gli conferisce la \textbf{massima libertà}: può decidere di pubblicare la classifica di una singola giuria, oppure può elaborare esternamente una classifica globale personalizzata e caricarla come file PDF. In entrambi i casi, una volta pubblicata, la classifica diventa disponibile per il download a tutti i partecipanti e giurati del contest all'interno dell'applicazione.

\section{Architettura del backend}\label{sec:architettura-del-backend}
Il backend è costruito interamente su Supabase e la sua architettura è definita da un'API sicura composta da un insieme di Funzioni RPC ed Edge Functions.

\subsection{Funzioni RPC (Remote Procedure Call)}\label{subsec:funzioni-rpc-(remote-procedure-call)}

Questa scelta è il fulcro dell'approccio di \textbf{accesso mediato da API}: nessun utente può effettuare operazioni dirette sul database, ma deve passare attraverso questo strato di controllo che garantisce che non possa compiere azioni a lui non concesse.

	-- Controlla in modo efficiente se qualche valore di tipo 'slider' nel payload JSON
	-- è al di fuori del suo range min/max definito o non è un numero valido.
	IF EXISTS (
	-- Utilizza una Common Table Expression (CTE) per "spacchettare" il payload JSON
	-- in una tabella temporanea di righe e colonne.
	WITH unpacked_votes AS (
	SELECT
	(value->>'voting_form_field_id')::uuid as field_id,
	(value->>'value')::text as value
	FROM jsonb_array_elements(p_votes_payload)
	)
	-- Seleziona le righe che violano le regole di validazione.
	SELECT 1
	FROM unpacked_votes uv
	-- Unisce i voti spacchettati con la tabella dei campi del form
	-- per ottenere i metadati di ogni campo (tipo, min, max).
	JOIN public.voting_form_fields vff ON vff.id = uv.field_id
	WHERE
	-- Applica il controllo solo ai campi di tipo 'slider'.
	vff.type = 'slider'
	AND (
	-- Condizione 1: Il valore non è una stringa di un numero intero.
	NOT (uv.value ~ '^-?\d+$')
	-- Condizione 2: Oppure, se è un intero, è fuori dai limiti.
	OR uv.value::integer < vff.slider_min_value
	OR uv.value::integer > vff.slider_max_value
	)
	) THEN
	-- Se anche solo una riga viola le condizioni, solleva un'eccezione
	-- e interrompe la transazione, impedendo l'inserimento dei dati.
	RAISE EXCEPTION 'Invalid vote value: A slider value is outside its allowed range or is not a valid number.';
	END IF;
	
	-- Se la validazione passa, la funzione procede con l'inserimento dei voti...

\section{Architettura di sicurezza: Principio del Minimo Privilegio e Accesso Mediato}\label{sec:architettura-di-sicurezza:-principio-del-minimo-privilegio-e-accesso-mediato}
La sicurezza è un requisito trasversale che ha guidato l'intera progettazione del backend.
È stato adottato un rigoroso modello basato sul \textbf{Principio del Minimo Privilegio (PoLP)}, il cui assunto fondamentale è negare l'accesso per default e concederlo solo in modo esplicito e controllato.

\subsection{Il Principio del Minimo Privilegio e l'API come Gatekeeper}\label{subsec:il-principio-del-minimo-privilegio-e-l'api-come-gatekeeper}
Tutte le tabelle del database hanno la \textbf{Row Level Security (RLS)} abilitata, con una policy di \texttt{DENY} implicita per tutte le operazioni.
Questo significa che la chiave API usata dal client Flutter (\texttt{anon\_key}) non ha, di per sé, alcun permesso di leggere o scrivere dati.

L'accesso ai dati è quindi interamente mediato da un'API sicura, composta da:
\begin{itemize}
	\item \textbf{Funzioni RPC \texttt{SECURITY DEFINER}}: per la maggior parte delle operazioni sul database.
	\item \textbf{Edge Functions}: per operazioni complesse e interazioni con servizi esterni.
\end{itemize}
Questa architettura garantisce che tutta la logica di autorizzazione (es.\ ``l'utente è l'organizzatore di questo contest?'') sia centralizzata e verificata lato server, aderendo al principio del minimo privilegio.

\subsection{L'Eccezione Necessaria: le Policy RLS per il Servizio Realtime}\label{subsec:l'eccezione-necessaria:-le-policy-rls-per-il-servizio-realtime}
Esiste un'eccezione mirata a questa regola.
Il servizio \textbf{Supabase Realtime}, che permette al client di sottoscrivere modifiche al database in tempo reale, basa il suo meccanismo di autorizzazione proprio sulle policy RLS della tabella.
Per permettere a un client di ``ascoltare'' le modifiche su una tabella, è necessario definire una policy di \texttt{SELECT} che gli conceda il permesso di lettura su quelle specifiche righe.

Questo ha richiesto l'implementazione di policy RLS di tipo \texttt{SELECT} esclusivamente per le due tabelle esposte al servizio Realtime: \texttt{messages} e \texttt{voting\_sessions}.
Questo è stato un adattamento necessario per integrare una funzionalità chiave, mantenendo la massima sicurezza su tutte le altre operazioni e tabelle.

Il seguente listato mostra la policy implementata per la tabella \texttt{voting\_sessions}, un esempio significativo di come l'autorizzazione sia stata definita in modo granulare anche in questo caso eccezionale.

% Esempio di policy RLS per il servizio Realtime.
\begin{lstlisting}[language=SQL, caption={Policy RLS di tipo SELECT per la tabella \texttt{voting\_sessions}, necessaria per il servizio Realtime.}, label={lst:rls_realtime_policy}]
	-- Abilita l'accesso in lettura alla tabella `voting_sessions`
	-- solo per gli utenti autorizzati a ricevere aggiornamenti in tempo reale.
	CREATE POLICY "Allow read access to organizers and involved jurors"
	ON public.voting_sessions
	FOR SELECT
	USING (
	-- Condizione 1: L'utente è l'organizzatore del contest a cui la sessione appartiene.
	(EXISTS (
	SELECT 1 FROM public.contests c
	WHERE c.id = voting_sessions.contest_id AND c.organizer_id = auth.uid()
	))
	OR
	-- Condizione 2: L'utente è un giurato che partecipa a questa specifica sessione di voto.
	(EXISTS (
	SELECT 1 FROM public.voting_session_jurors vsj
	WHERE vsj.voting_session_id = voting_sessions.id AND vsj.juror_id = auth.uid()
	))
	);
\end{lstlisting}

\subsection{Misure di Sicurezza Aggiuntive}\label{subsec:misure-di-sicurezza-aggiuntive}
Oltre al modello ibrido RLS/RPC, la sicurezza del sistema è rafforzata da altre misure:
\begin{itemize}
	\item \textbf{Protezione delle API Esterne}: le chiavi segrete per servizi come Resend e Google Places sono memorizzate in Supabase e accessibili solo dalle Edge Functions.
	\item \textbf{Protezione dei file}: nessun file nello Storage è pubblico.
	L'accesso avviene solo tramite \emph{signed URL} temporanei generati lato server.
\end{itemize}

\subsubsection{Gestione dei Giurati Semplici: il Pattern dell'Autenticazione Anonima}
Una delle sfide più complesse è stata quella di permettere a un \emph{Simple Juror} di votare in modo sicuro senza obbligarlo a creare un account permanente.
Risolvere questo problema solo con un token temporaneo sarebbe stato insicuro, poiché non avrebbe permesso di tracciare in modo affidabile se l'utente avesse già votato.

Per risolvere questa sfida, è stato implementato un pattern basato sull'\textbf{autenticazione anonima} offerta da Supabase.
Questo approccio è un'applicazione diretta del Principio del Minimo Privilegio.
Il flusso è il seguente:
\begin{enumerate}
	\item L'utente inserisce il token della giuria semplice.
	La RPC \texttt{juror\_access\_voting\_as\_simple\_juror} valida il token.
    \item Se il token è valido, l'applicazione chiede all'utente di inserire il proprio nome e, subito dopo, il client esegue una chiamata a Supabase per effettuare un \textbf{sign-in anonimo}.
    \item Supabase Auth crea un account utente a tutti gli effetti, ma marcato come ``anonimo'', e restituisce un JWT valido.
	Da questo momento, anche l'utente anonimo ha un \texttt{auth.uid()} univoco.
    \item L'\texttt{AuthBloc} nel client entra in uno stato ``autenticato ma anonimo''.
    \item L'\texttt{AuthGuard}, riconoscendo questo stato, applica una logica di navigazione restrittiva: permette l'accesso solo alle pagine strettamente necessarie per la votazione (es.\ la procedura di voto), bloccando tutte le altre sezioni dell'app (es.\ impostazioni, dashboard).
    \item Al termine della sessione, quando l'utente effettua il logout, viene invocata la Edge Function \texttt{user-delete-account}.
	Poiché l'utente possiede un JWT valido, è autorizzato a chiamare questa funzione, che elimina in modo sicuro e permanente l'account anonimo appena utilizzato.
\end{enumerate}
	
Questo pattern offre enormi vantaggi:
\begin{itemize}
	\item \textbf{Esperienza Utente Fluida}: L'utente non percepisce la creazione di un account, ma solo l'inserimento del proprio nome.
	\item \textbf{Sicurezza Robusta}: Ogni azione del giurato semplice (come l'invio dei voti) è autenticata e legata a un \texttt{uid} univoco, prevenendo abusi.
	\item \textbf{Riutilizzo dell'Architettura}: Permette di riutilizzare la stessa logica di sicurezza (RLS, RPC che controllano \texttt{auth.uid()}, \texttt{AuthGuard}) sia per gli utenti normali che per quelli anonimi, senza dover creare un sistema di autorizzazione parallelo e meno sicuro.
\end{itemize}

\section{Progettazione e Implementazione degli Strumenti di Amministrazione}
\label{sec:admin_tools}

Oltre all'applicazione destinata agli utenti finali, un sistema software robusto richiede strumenti adeguati per la sua gestione, moderazione e manutenzione.
Per Swift Contest, si è deciso di non sviluppare un'applicazione admin da zero, ma di utilizzare \textbf{Retool}, una piattaforma low-code specializzata nella creazione rapida di strumenti interni.

\subsection{Esigenza di un Pannello di Amministrazione}\label{subsec:esigenza-di-un-pannello-di-amministrazione}
La necessità di un pannello di amministrazione nasce da requisiti operativi critici non gestibili dagli utenti standard:
\begin{itemize}
    \item \textbf{Gestione Utenti}: la capacità di visualizzare tutti gli utenti registrati, verificarne l'attività e, in caso di abuso, procedere con l'eliminazione dell'account.
    \item \textbf{Moderazione Contenuti}: la possibilità per un amministratore di ispezionare e, se necessario, rimuovere forzatamente un contest che viola i termini di servizio.
\end{itemize}

\subsection{Scelta di Retool per lo Sviluppo Rapido}\label{subsec:scelta-di-retool-per-lo-sviluppo-rapido}
La scelta di Retool è stata strategica e motivata da:
\begin{itemize}
    \item \textbf{Velocità di Sviluppo}: ha permesso di costruire un'interfaccia admin funzionale in poche ore, invece che in settimane, concentrando le risorse di sviluppo sull'applicazione principale.
    \item \textbf{Integrazione Nativa}: si integra nativamente con database PostgreSQL e API REST, permettendo di interfacciarsi facilmente con l'infrastruttura Supabase.
    \item \textbf{Sicurezza Configurabile}: offre meccanismi per gestire segreti (come le chiavi API) e configurare le chiamate in modo sicuro.
\end{itemize}

\subsection{Architettura di Comunicazione Sicura tra Retool e Supabase}\label{subsec:architettura-di-comunicazione-sicura-tra-retool-e-supabase}
La sicurezza è stata la priorità nella progettazione dell'integrazione.
L'accesso ai dati non è mai diretto, ma mediato da un'API sicura esposta dal backend Supabase, con due meccanismi distinti:

\subsubsection{Accesso in Lettura tramite Utente Dedicato e Funzioni RPC}
Per le operazioni di sola lettura (es.\ visualizzare la lista di utenti), è stato creato un utente PostgreSQL dedicato, \texttt{retool}, con permessi minimi.
Le query da Retool invocano funzioni RPC con prefisso \texttt{admin\_*}, che al loro interno verificano che il chiamante (\texttt{session\_user}) sia esattamente \texttt{retool}, bloccando qualsiasi altro tentativo di accesso.

% Inserire qui un estratto di codice PL/pgSQL che mostra la validazione del session_user in una funzione RPC amministrativa.
\begin{lstlisting}[language=SQL, caption={Validazione del chiamante all'interno di una funzione RPC per l'amministrazione.}, label={lst:rpc_admin_validation}]
	-- Estratto da una funzione come 'admin_get_all_accounts()'
	
	CREATE OR REPLACE FUNCTION admin_get_all_accounts()
	RETURNS SETOF profiles -- o un altro tipo di ritorno
	LANGUAGE plpgsql
	SECURITY DEFINER
	SET search_path = public;
	AS $$
	BEGIN
	-- --- 1. CONTROLLO DI SICUREZZA ---
	-- Questa è la prima operazione eseguita dalla funzione.
	-- 'session_user' è una variabile speciale di PostgreSQL che contiene
	-- il nome dell'utente della connessione corrente (in questo caso, 'retool_user').
	
	IF session_user <> 'retool' THEN
	-- Se il chiamante non è l'utente 'retool' designato,
	-- la funzione solleva un'eccezione e interrompe immediatamente l'esecuzione.
	RAISE EXCEPTION 'Permission denied: This function can only be called by the admin user.';
	END IF;
	
	-- --- 2. ESECUZIONE DELLA LOGICA ---
	-- Se il controllo di sicurezza passa, la funzione procede
	-- con l'esecuzione della query per recuperare i dati.
	RETURN QUERY
	SELECT * FROM public.profiles;
	
	END;
	$$;
\end{lstlisting}

\subsubsection{Operazioni di Scrittura tramite Edge Functions e API Key}
Per le operazioni che richiedono un'orchestrazione complessa o l'interazione con servizi esterni al database, come l'invio di email o la manipolazione di file nello Storage, sono state implementate delle \textbf{Edge Functions}.
Funzioni critiche come \texttt{admin-delete-account} e \texttt{admin-delete-contest} rientrano in questa categoria, poiché devono non solo modificare i record del database, ma anche eliminare tutti i file associati (immagini, file) dallo Storage per garantire una pulizia completa.

Queste funzioni sono protette da un meccanismo di autenticazione server-to-server per garantire che possano essere invocate solo da un client autorizzato come Retool:
\begin{enumerate}
    \item Retool, nell'eseguire l'azione, invia una richiesta HTTP \texttt{POST} alla Edge Function, includendo un header personalizzato: \texttt{X-API-Key}.
    \item Il valore di questa chiave è un segreto memorizzato sia in Retool che nel in Supabase.
    \item La Edge Function, come primo passo, confronta la chiave ricevuta con quella memorizzata nei suoi segreti.
    Se non corrispondono, la richiesta viene immediatamente respinta con un errore 401 (Unauthorized).
\end{enumerate}
Questo approccio garantisce che solo un'applicazione autorizzata possa invocare queste potenti funzioni, proteggendo il sistema da accessi impropri.

% Inserire qui un estratto di codice TypeScript che mostra la validazione della X-API-Key in una Edge Function amministrativa.
\begin{lstlisting}[language=TypeScript, caption={Validazione della chiave API all'interno di una Edge Function amministrativa.}, label={lst:api_key_validation}]
	// Estratto da una Edge Function come 'admin-delete-account/index.ts'
	
	// ... (all'interno della funzione Deno.serve)
	try {
		// --- 1. API KEY AUTHORIZATION ---
		// Questo pattern è usato per tutte le chiamate server-to-server da Retool.
		
		// Legge la chiave API inviata dal client (Retool) nell'header.
		const apiKey = req.headers.get('X-API-Key');
		
		// Recupera la chiave segreta memorizzata in modo sicuro nel Vault di Supabase.
		const secretKey = Deno.env.get('RETOOL_API_KEY');
		
		// Primo controllo: verifica che il segreto sia stato configurato.
		if (!secretKey) {
			throw new Error("RETOOL_API_KEY is not set in Supabase secrets.");
		}
		
		// Secondo controllo: confronta la chiave ricevuta con il segreto.
		// Se non corrispondono, la richiesta viene immediatamente respinta.
		if (apiKey !== secretKey) {
			return new Response(
			JSON.stringify({ error: "Unauthorized. Invalid API Key." }),
			{
				headers: { ...corsHeaders, "Content-Type": "application/json" },
				status: 401, // 401 Unauthorized
			}
			);
		}
		
		// --- 2. PROSECUZIONE DELLA LOGICA ---
		// Se la validazione ha successo, la funzione procede con
		// l'esecuzione delle operazioni amministrative.
		
		// ... (logica per eliminare l'utente, i file, ecc.)
		
	} catch (error) {
		// ... (gestione degli errori)
	}
\end{lstlisting}
